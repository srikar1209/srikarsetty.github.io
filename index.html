Baggage screening depends on spotting rare, dangerous items in cluttered X-ray scans. The most critical classes, like guns and bullets, are exactly the ones detectors see least during training.

Clinical Trial Data Validation
& Compliance Orchestration Platform

Type
Multi-Agent System
Stack
LangGraph · MCP · Streamlit
Domain
Clinical Data Compliance
Data
5,000 synthetic visits

Overview

A clinical trial collects thousands of patient visits from many sites, and every record has to be checked before it can be used: is it complete, is it possible, is anything medically worrying? Much of this is still done by hand. It is slow, and real problems get lost among routine records.

Most records only need fixed checks. Some, like a serious adverse event or a very unusual lab value, need a person. Others are data entry mistakes the site should fix. This platform sorts records into those three groups, explains every decision, keeps a tamper-evident audit log, and delivers cleared records to the next system without losing any.

All data is synthetic: study "CT-201" compares a made-up drug, XR-17, against placebo across 1,000 patients and 6 sites.

Architecture

Four agents are connected as a LangGraph graph: validate → detect anomalies → route → report. Agents 1–3 hold no check logic themselves; they call deterministic tools served by an MCP server over stdio, in batches of 500 records (10 calls per tool, 30 in total). Run with --local, the same functions are called directly with identical results. Every audit entry records which tool was used and whether it ran via MCP or locally.

5,000 records ─► Validate ─► Z-score ─► Route ─► Report
                    └───────────┴──────────┴──► Audit log (hash chain)

AUTO_CLEAR   ─► Submission gateway ─► outside system
HUMAN_REVIEW ─► review queue (decision also logged)
QUERY_SITE   ─► back to the site to fix

How It Works

01
Synthetic Data
5,000 visits with planted problems: missing fields, visits before consent, impossible ages and blood pressures, wrong arm codes (XR17), exact duplicates, real ALT outliers, and a hidden liver safety signal at SITE-04.
02
Agent 1 · Validate
Required fields, allowed arms, plausible ranges (age 18–90, systolic BP 70–220 mmHg, ALT 3–2000 U/L, creatinine 0.2–10 mg/dL), visit not before consent, AE grade present when an AE is reported, and duplicate detection.
03
Agent 2 · Z-score
Z-scores ALT, creatinine, and systolic BP against the mean and standard deviation of the same treatment arm. Stats come from valid records only, so bad data cannot distort them. |z| ≥ 3 is flagged as an outlier.
04
Agent 3 · Route
First matching rule wins: any data error → QUERY_SITE; serious AE, AE grade 3+ (CTCAE scale), or a lab outlier → HUMAN_REVIEW with HIGH/MEDIUM priority; everything else → AUTO_CLEAR.
05
Agent 4 · Report
Computes counts, top error types, and a per-site safety signal (share of XR-17 visits with ALT z ≥ 3, then z-scored across sites). A local Llama 3.2 model via Ollama writes the summary from those facts only; a fixed template is the fallback.
06
Audit Log
Append-only SQLite log storing record, agent, decision, reason, rule version, and timestamp, each chained to the previous entry with a SHA-256 hash. verify() pinpoints the first altered entry. Entries can also be streamed to a Kafka topic.
07
Submission Gateway
Sends cleared records to a simulated outside system (8% random errors, 20 calls/s limit, a 30-second outage) through a token-bucket rate limiter, exponential backoff with jitter, a circuit breaker (opens after 5 consecutive failures, 30 s cooldown), and a dead-letter queue.

Review App

A five-page Streamlit app reads the results database:

  • Overview: pipeline diagram, routing counts, review reasons, and data errors.
  • Human review queue: high-risk records; every reviewer decision requires a comment and is written to the audit log.
  • Record audit trail: every entry for one record, plus a one-click check of the whole hash chain.
  • Site safety signals: ALT outlier share and ALT values by site.
  • Submission gateway: send once vs. immediate retry vs. gateway against the same flaky system.

Design Choices

  • Rules decide, the LLM only writes. Safety decisions must be predictable and explainable.
  • Bad data is never dropped. It goes back to the site with the reason.
  • Z-score stats come from valid records only, so errors cannot distort them.
  • Every decision stores the rule version, so you always know which rules made it.
  • Tools sit behind a standard interface. Agents don’t know whether they call MCP or local functions.

Limitations

  • All data is synthetic, and the planted errors are simpler than real ones.
  • Rule thresholds (ranges, z ≥ 3, grade 3+) are for demonstration, not from a real protocol.
  • The outside system is simulated; real systems fail in other ways too.
  • The audit log is tamper-evident, not tamper-proof: it shows that an entry changed, not who changed it.

Sim2Find: Agent-Based Search
for Missing People with Dementia

Event
HackUMass XIV · Team Rescuers
Type
Agent-Based Model + Bayesian Inference
Area
Amherst, MA · 10 m grid
Live Demo
sim2find.us

Overview

Older people with dementia who walk away from home often don’t know they’re lost. They don’t call for help or answer when searchers shout their name; they just keep walking. In Koester’s dementia incident data (ISRID), most keep going in one direction until something stops them, and 95% of those found within 24 hours were alive, versus 77% found later. Yet searches often still start with a circle around the house.

Sim2Find turns that research, plus whatever clues come in, into a map that tells a team where to look first. Given where and when the person was last seen, it simulates thousands of possible walks on the real Amherst terrain and returns a heat map, not a pin: red areas are where most walks ended.

As clues arrive, the map updates. A sighting pulls the heat toward that place; a camera that saw nothing or an area already searched cools those spots. Witness reports can be typed in plain words and an LLM drafts a structured clue, but a person always confirms it. The walking itself is done by the agent-based model, never the LLM.

Heat Map Before and After Clues

How It Works

01
Terrain Grid
Real Amherst terrain on a 10 m grid built from OpenStreetMap, USGS 3DEP elevation, and NLCD 2021 land cover, with road traffic levels, buildings, fences, woods, wetland, streams, and low ground.
02
Agent-Based Walkers
Each walker follows rules from Koester’s lost-person research on dementia: most go straight until stuck, 66% cross roads instead of following them, they tend to go downhill, can stop at buildings, water, or rough terrain, and can be spotted by the public on busy roads.
03
Calibration
22 rule numbers tuned with Bayesian optimization (Optuna TPE, 400 settings over 20 start points) until walkers match 16 ISRID statistics on distance, find location, and elevation change. Every rule is labeled DATA, EXPERT, or ASSUMPTION.
04
Clue Inference
Clues reweight walkers like a particle filter. A sighting also restarts 10,000 new walkers from the sighting place; camera negatives and searched areas cool their cells; “still missing” down-weights walkers that spent time on busy roads.
05
Heat Map
Probability per grid cell at any chosen minute. 5% of the map always falls back to distance rings around the latest known place, so no area is ever zero. The UI shows the hottest cells holding 80% of the probability and the top three priority areas.
06
LLM Clue Extraction
Free-text witness reports are converted into draft clues (Gemini, with Claude as an alternative), with reliability set to high, medium, or low. A guided chat asks for missing coordinates, times, or radius, and nothing updates the map until a person accepts it.

Web App

  • Case setup: last-seen point and time, estimate-as-of time (up to four hours later), optional departure direction and goal place.
  • Live heat map over OpenStreetMap tiles with a time slider, top-three priority areas, and nearby named features.
  • Clue workflow: sightings, camera negatives, and searched areas pinned on the map, with editable reliability, miss rate, detection, and radius; clues can be edited or removed and weights recompute.
  • Deployment: lightweight Python server (NumPy + Pillow) on Render at sim2find.us, with pre-baked terrain tiles and a cached demo run of 5,000 walkers.

Limitations

  • The demo case (Walter) is fictional.
  • Benchmark cases are built from published ISRID statistics, not real case records.
  • The map’s probabilities are model estimates, not validated for real search decisions.
  • The next-best-check suggestion is not implemented yet. Next step: test against real solved cases with a search team.

MedBot: Fine-Tuned Medical
Chat Assistant with RAG

Institution
Mahindra University
Timeline
Jan 2024 – Jun 2024
Model
Mistral 7B v0.3 (4-bit, LoRA)
Data
HealthCareMagic · MedQuAD

Overview

People often describe their symptoms online before seeing a doctor. General-purpose language models can answer, but they don’t sound like a doctor, rarely say when to get care in person, and don’t show where their facts come from.

MedBot is a small, open model that replies the way a doctor would on a health Q&A site: what the problem may be, what to do next, and when to see someone in person. With RAG turned on, it also retrieves the closest passages from NIH health documents (MedQuAD) and lists their source links under the answer.

Mistral 7B is loaded in 4-bit and fine-tuned with LoRA on real doctor answers from HealthCareMagic. The whole pipeline runs in one Colab notebook on a free T4 GPU in about 1 to 1.5 hours.

Educational project, not medical advice.

How It Works

01
Cleaning
HealthCareMagic answers are full of politeness ("Hi, thanks for your query", "I understand your concern", "Regards, Dr. X"). A regex-based cleaner fixes glued sentences (e.g. "LIVERHi", "advice.As") and strips greetings, thank-yous, sign-offs, and doctor names so the model learns the medical content.
02
Noise Filtering
Each pair is dropped for the first rule it fails, with the reason recorded: answer under 25 words, contact details or self-promotion, duplicate question, greeting-only answer, over 600 words (too long for 1,024 tokens), question under 5 words, or garbled text.
03
Held-out Split
Cleaned pairs are shuffled once with a fixed seed. 100 questions are held out as a test set and never trained on (an assertion guards against leakage); 5,000 pairs are used for training.
04
Prompt Format
One prompt template for both training and testing, with Instruction, optional NIH Reference, Patient, and Doctor sections. An end-of-sequence token is appended to each training example so the model learns to stop.
05
Fine-tuning
Mistral 7B v0.3 in 4-bit with LoRA (r = 16, α = 16) on all attention and MLP projections, about 0.6% of parameters trainable. 1 epoch, learning rate 2e-4, cosine schedule, 8-bit AdamW, using Unsloth and TRL.
06
RAG
MedQuAD answers are cut into ~150-word chunks with 30-word overlap, each keeping its source URL, and embedded with all-MiniLM-L6-v2. For each question, the 3 closest chunks by cosine similarity are added to the prompt and cited under the answer.
07
Evaluation
Base model vs. fine-tuned vs. fine-tuned + RAG on the same 100 held-out questions, scored against the real doctor’s answer with ROUGE-L and BERTScore F1.

Engineering

  • GPU-free, tested helpers. Parsing, cleaning, filtering, splitting, prompting, chunking, retrieval, and ROUGE-L live in one plain-Python module with unit tests.
  • Single source of truth. A build script generates the Colab notebook from the tested module, so notebook and code never drift.
  • Reproducible. Fixed seeds throughout; the notebook saves the LoRA adapter, results, examples, cleaning report, test set, and training log as one zip.
  • Try it. An ask_medbot() helper answers any question with or without RAG and prints its NIH sources.

Limitations

  • HealthCareMagic answers come from online doctors of varying quality; the model learns their style and their mistakes.
  • ROUGE-L and BERTScore measure similarity to one doctor’s answer, not medical correctness. No clinician has reviewed the outputs yet.
  • The test set is 100 questions, so small score differences are not meaningful.
  • RAG only covers topics in MedQuAD, and the retriever can return a related but wrong topic.
  • Next step: have clinicians rate a sample of answers for correctness and safety.
